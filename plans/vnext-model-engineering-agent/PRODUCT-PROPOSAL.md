版本：方案草案 0.1｜日期：2026-09-11｜状态：待评审，非实现完成声明。

配套：[迭代计划](ITERATION-PLAN.md) · [待决事项](DECISIONS.md)。

## 1. 产品定义与目标用户

**产品承诺：用户描述模型目标、提供合法数据与资源约束，Agent 组织模型研究、环境搭建、代码适配、试验、训练和验证；产品持续维护可信的模型研发证据，并帮助用户改进业务效果。**

主要用户是希望获得模型能力、但不希望自己组织完整算法工程过程的 AI 产品经理、独立开发者和业务团队。算法/研发人员是方案审查与扩展的协作者，不应成为每个新场景启动前必需的插件开发者。

“通用”与“专业”的边界：

- 任务类型开放：图片分类、实体识别、语音识别、语音合成、OCR 等进入同一模型工程工作体系，不建立有限场景入口白名单。
- 工程实现因任务而异：同一个 Agent 可以组织不同代码、框架、数据结构和评测方法，不要求所有任务共享同一个训练函数。
- 适配属于任务工作：缺少预装方案时，目标能力是由 Agent 在受控环境构建、验证所需工程方案，而不是只输出“请研发接插件”。
- 实际支持由证据声明：接收需求、找到仓库、完成静态分析、试跑成功、训练完成、质量达标分别记录；分析报告不是训练成功。
- 不保证任意任务必成功：数据、许可证、依赖、资源、安全条件和质量要求仍可能阻止完成。阻断必须具体、可追溯，不以固定类型名单代替实际判断。

任务方向是开放目标，不代表本版已交付 OCR、NER、ASR 或 TTS。各类具体能力在真实验证前保持未验证状态。

## 2. 三项需要证明的领域优势

通用编程 Agent 原理上也可以编写评测、调参和记录脚本；我们的差异必须来自默认、持续维护的专业机制及其可测量收益。

| 领域优势 | 产品机制 | 持续沉淀的资产 | 用户收益 |
| --- | --- | --- | --- |
| 可信选型与验收 | 业务目标转成指标与重要切片；建立基线；冻结评测协议；检查泄漏和证据充分性；联合比较质量、延迟、体积与约束 | 验收规则、开发评测集、切片定义、基线与模型比较证据 | 知道哪个方案真正适用，以及哪些结论尚不能成立 |
| 预算内实验决策 | 根据错误与资源实测提出假设；用小规模对照验证；记录试验预算与收益；停止无收益路线 | 数据/环境特征、兼容性、实测资源曲线、失败模式、配置及结果 | 更少无效试验，更快得到达标方案 |
| 可验证的持续改进 | 错例归类→提出改动→开发集实验→目标切片与旧能力回归→独立终测 | 开发错例库、回归矩阵、干预与结果记录、业务偏好 | 改善目标问题，同时知道有没有损伤原有能力 |

任务列表、训练曲线、日志和交付包是必要体验基础，不能单独证明竞争优势。专家数量、提示词长度、Recipe 数量也不是优势指标。

总体目标指标是“固定任务与预算下的独立验收达标率”；辅以达标时间/总成本、人工介入量、错误放行率、回归率和干净环境复现率。M0 冻结指标方法与基线预算；可执行基线在 M2 条件具备后测量，再于正式优势对照/留出评测前由人冻结收益阈值。具体任务的业务质量门仍须在该任务训练前确认，不能由 Agent 为通过测试自行设定。

## 4. 目标产品架构

### 4.1 五层产品结构

| 层级 | 构成 | 职责与来源 |
| --- | --- | --- |
| PC 用户工作区 | 任务列表、主对话、任务摘要、右侧证据工作台、执行详情 | 自研 Studio；一个入口，不展示为多个独立产品 |
| 模型研发能力域 | 目标与验收、模型研究、数据工程、实验与训练、评测与诊断、交付与复用 | 自研领域能力；复用已有实现并扩展，不按模型任务类型复制产品 |
| 工程 Agent 与决策 | 需求澄清、研究、编程、实验计划、诊断；按需委派 | 复用 DSH 的 Agent Loop/会话/工具调度；自研领域策略、工具桥接、授权与经验读取；工程能力须实测，不由“多 Agent”名称推定 |
| 可信执行与证据 | 任务/数据/合同/Run 身份，Worker 作业、资格验证、独立评测、审批、资源预算、事件与制品 | 保留 Model Harness 为权威领域内核；新增隔离执行服务并接回同一事实源 |
| 模型与环境资源 | HF/GitHub 来源、依赖与模型缓存、授权数据、经过验证的计算环境 | 外部资源，不是 DSH 自带训练能力；下载、执行、缓存与复用受范围和许可证约束 |

以上是职责分层，不是五级导航。DSH 前端不是用户必开页面，也不是训练计算服务。

### 4.2 六个能力域的二级功能

| 能力域 | 二级功能 | 主要输出与边界 |
| --- | --- | --- |
| 目标与验收 | 输入输出澄清、业务错误成本、质量/延迟约束、预算、验收确认 | TaskSpec 与合同；Agent 提议，用户掌握标签含义和不可变门槛 |
| 模型研究 | 搜索资料与仓库、固定版本/许可、候选比较、现成模型试用路线、训练路线选择 | 来源候选、证据、计划；研究文本不得下命令或授权执行 |
| 数据工程 | 文件体检、标注结构、字段/样本映射、去重与泄漏检查、切分、数据版本、开发错例 | DatasetVersion 与报告；缺少标注/授权时请求补充，不捏造训练数据可用性 |
| 实验与训练 | 环境准备、任务代码构建、最小试跑、资格验证、基线、候选试验、训练、预算/取消/恢复 | BuildAttempt、QualificationRun、已注册版本与 Run；试跑不冒充正式训练 |
| 评测与诊断 | 冻结评测方法、业务切片、模型比较、错误归类、假设与对照、回归检查、独立终测 | EvaluationReport、实验决策与诊断；优化不得读取最终测试集用于选择 |
| 交付与复用 | 新样本推理、模型/环境/接口说明、包校验、干净环境加载、经验入库与适用性检查 | InferenceCheck、Bundle、受控经验记录；下载不等于部署，代码/经验复用不等于共享客户数据 |

研究、编程、数据和评测是职责，不强制新增同等数量的常驻 Agent。优先验证单个强工程 Agent 与独立校验器，只有独立产物或权限边界确有收益才拆分委派。

## 5. 三条产品旅程

### 5.1 未预装方案的新任务：通用性验证

以未预注册的实体识别任务为开发候选，最终留出任务在候选代码冻结后揭示；这不是新的任务白名单。

1. 用户描述要从什么文本提取哪些实体，Agent 确认必要标注、使用方式和约束。
2. Agent 搜索并比较来源、确认不可变版本，形成包含数据、资源与验收方式的计划。
3. 已有兼容方案则复用；没有则进入动态工程路径，构建数据转换、训练、推理与产物接口。
4. 在批准的隔离环境与小预算内完成资格试跑；失败保留证据，按有效修复政策继续或请求用户决策。
5. 独立验证接口、数据适配、最小训练/推理与产物；人批准精确资格证据后注册动态 Recipe/Adapter，再按合同和执行授权创建正式 Run。
6. 训练、评测、新样本验证、交付和干净环境消费同属原任务，用户无需另建插件项目。

无预装 Recipe 不是目标版的最终拒绝理由；但资格验证和注册不能被跳过。动态生成后经过验证的 Recipe 是规范化执行产物，不是需要用户预先开发的入口票据。

### 5.2 现成模型 → 判断是否需要训练

用户可以只想试模型，不一定要训练。来源选择后先获得真实推理与开发评测结果；若满足业务约束，可以交付既有模型的使用方案；不满足则提出数据/推理/微调等候选路径，说明依据与预算。基线推理、资格试跑、候选训练和正式训练分别记录，不制造空训练 Run。

为此使用 task-owned 的 `ModelTrial`，绑定来源快照、模型文件摘要、环境、输入版本、授权与结果。2026-09-12 首版已实现兼容 ONNX 的单图 CPU 试跑记录，见当前迭代证据；尚未实现任意模型的动态适配。当前 InferenceCheck/EvaluationReport/Bundle 主要绑定训练 Run，不能直接宣称已经支持完整无训练交付旅程；需冻结它们对“模型试用或训练 Run”的显式类型化引用与兼容迁移。ModelTrial 复用同一任务和执行服务，不另建平行任务系统。

若一个模型需要 remote code 或自定义推理代码，即便只是“试一下”，也适用相同隔离与来源授权规则。

### 5.3 错例 → 改进 → 防退化：第一条专业优势旅程

首个开发样例建议使用既有图片分类能力的“整图缺陷分类”，明确不是目标检测：

`初版开发评测 → 发现光照/材质切片问题 → 提出数据或模型假设 → 小规模对照 → 验证目标改善与旧类别回归 → 冻结候选 → 独立终测 → 可复验交付`

用户补充的错例进入开发/诊断数据，不混入仍需保持独立的最终测试集。不能因为某次总体分数上涨就断言假设成立；报告对照条件、改善范围、无效尝试和未决问题。

这条旅程用于验证领域优势；另用未预装任务验证通用性。二者共用执行、数据和证据架构，不发展成相互独立的演示工程。

## 6. 对象所有权：扩展现有事实源，不另造平台

产品对用户称“模型工程任务”，内部继续使用 `TrainingTask` 和兼容包 `model_harness`。

下表是逻辑设计，不是新增 API 已存在的声明。M0 必须以当前代码字段与[既有对象模型](../v0.9-universal-byom/object-model.md)建立迁移对照；历史文档字段不直接覆盖现有实现。

| 对象/关系 | 唯一拥有方 | 本轮设计要求 |
| --- | --- | --- |
| 对话与 TrainingTask | Conversation / Workspace | 咨询不建训练任务；晋升保持身份与历史，防重复创建 |
| TaskSpec、合同 revision | Task / Contract 服务 | 目标、数据或门槛变化形成新版本；旧确认按依赖失效 |
| 来源候选、绑定和快照 | Source store | 查看/收藏/研究不是执行选择；固定版本批准不自动扩大为训练授权 |
| 当前执行选择 | TrainingPlanRevision 与 task-owned 关联 | 推荐扩展现有计划关系，不新增平行“项目任务”；切换需展示影响并保留退回路径 |
| DatasetVersion 与切分 | Data 服务 | 同一数据版本贯穿训练和评测；训练/开发/终测边界可核验 |
| EnvironmentLock、ResourceFitReport | Environment / Resource 服务 | 描述实际执行环境；宿主机检测与 Worker 内可用能力分开 |
| BuildAttempt、候选代码与修复差异 | Build 服务 | 追加版本和父子关系；代码、依赖、输入、权限改变后资格与批准重新校验 |
| QualificationRun | Qualification 服务（需补齐） | 按申报的推理/训练能力执行资格验证；推理资格不得被用于创建训练 Run；生成证据供独立注册审批 |
| RecipeVersion / AdapterVersion | 现有版本注册服务 | 精确证据批准后注册；复用范围必须与原验证条件匹配 |
| ModelTrial（首版已实现） | `model_trials.py` | 已支持兼容 ONNX 的无训练试跑；绑定来源/模型/环境/输入/授权，不使用空 Run 冒充身份 |
| Worker job | `oci_jobs.py` 首版 CPU 执行器 | 技术执行记录；当前接入 ModelTrial，其余 BuildAttempt/QualificationRun/Run 尚待接线；不成为第二种用户任务 |
| Run、InferenceCheck、EvaluationReport、Bundle | 对应现有领域服务 | 当前结果按有效版本关系计算；需明确兼容训练 Run 与无训练试用的证据引用，不能仅解除 Run 校验 |
| 开发错例、切片、实验假设与结果 | Data / Evaluation / Plan 服务扩展 | 不复制数据；引用版本与样本身份；训练决策与终测结果权限分离 |
| 经验记录 | 受控经验仓（需新增） | 引用已验证对象；记录适用条件、失败与撤销；默认任务/工作区隔离 |

所有 Agent/tool/worker 投影继续携带 `task_id / agent_run_id / session_id / turn_id / call_id` 与显式委派血缘。新作业身份只能追加关联，不能替换或猜测原身份。ObjectRef 由后端真实结果产生。

## 7. 工程执行与验证边界

两条入口最终汇入同一个领域执行协议：

| 路径 | 入口到正式运行 |
| --- | --- |
| 已验证快捷方案 | 校验适用条件 → 当前合同与授权 → 受约束运行 → 独立评测 |
| 新模型工程方案 | 固定来源/计划 → 受控构建 → 真实资格验证 → 精确证据批准注册 → 当前合同与授权 → 受约束运行 → 独立评测 |

这里的“运行”可为 ModelTrial 或 TrainingRun，必须显式区别。仅推理方案验证推理、数据适配、评测和交付，不要求伪造训练；申报训练能力则必须完成真实最小训练。后端严格限制注册版本所获能力，不让推理资格成为训练许可。

目标控制要求：

- 不向研究插件提供任意宿主 shell；工程工具只能访问任务隔离目录、允许网络、限定资源及必要凭据代理。
- 动态注册不能把不可信候选 Python 安装或导入 Studio 宿主进程。控制平面读取经过校验的声明与摘要，使用可信代理调用 Worker；候选训练/推理代码始终在隔离边界内。既有开发者审核插件的加载机制不能直接承接动态代码。
- 初次资源信息不完整时，可申请明确上限的资格试跑预算；试跑实测后形成正式资源判断。不能把暂定估算伪装成训练可行结论。
- Worker 作业脱离单个聊天回合管理；使用幂等身份、租约/心跳、总超时和取消升级。状态不明时先对账，禁止盲目重复启动。
- 编码者不能通过同时修改评测器与模型来证明成功。评测协议、实现和校准样例在候选实验前验证/冻结；最终测试数据与答案不挂载到工程 Agent 环境。
- 对新任务可以构建评测候选，但必须通过独立校验与必要的人审后使用。TTS 等主观维度需要相应人工评价协议，不能只用一个代理分数宣布可用。
- 最终测试失败后，不把逐条终测反馈回流调参再宣称同一终测独立；后续研发按污染/新验收版本政策处理。
- 模型快照、代码/环境摘要、数据版本、评测实现、授权与预算绑定同一次尝试；变更不会原地覆盖旧证据。
- 不同模型文件格式通过经验证的产物声明交付，而非任意目录压缩；交付白名单、许可证、私有数据排除和消费方加载验证同样适用于动态任务。

GPU 是真实需求，不是无限后延的愿景；M0 选择可验证的目标后端，M2 按批准范围验证设备可达性、资源约束、取消和复现。没有通过前保持不可用，不能以检测到 MPS/CUDA 替代验证，也不擅自购买云资源。

## 8. PC 交互规格

一个任务、一段主对话、一个自适应证据工作台；只验收 PC：1280×800、1440×900、1920×1080。

| 区域 | 用户可做什么 | 不做什么 |
| --- | --- | --- |
| 左侧任务列表 | 新建、搜索、打开、查看归档、恢复 | 不维护第二套训练任务存储 |
| 中央对话 | 描述目标、追问、上传、决策、补充、停止；查看对应回合的执行摘要 | 不强制逐字段填表，不用散文宣告完成 |
| 当前任务摘要 | 看目标/数据/方案版本、真实阶段与必要下一步 | 不把等待批准和正在执行合并成“运行中” |
| 右侧工作台 | 候选比较、数据预览、实验对照、曲线、错例、版本差异、产物验证 | 不复制一套向导或审批真值；关闭面板不改变任务 |
| 执行详情 | 查工具、日志、来源、作业与异常证据 | 不要求普通用户理解内部会话 ID 才能操作 |

交互语义必须先定义再实现：

| 用户动作 | 必须产生的效果 |
| --- | --- |
| 审批时问“为什么” | 只读解释；对象/摘要/范围不变时保留待决审批，不默认为同意 |
| 修改目标、数据或门槛 | 展示影响，确认后新建版本；旧审批不可消费，旧结果作为历史而非当前成果 |
| 查看或研究另一个模型 | 不改变当前执行选择；明确采用才切换计划，并给出返回已验证方案的路径 |
| 执行中普通补充 | 明示是排队、并行讨论还是将影响下一轮；不能假装当前作业已被改变 |
| 请求停止 | 有明确控制通道，不排队到回合结束；区分停止 Agent/后台作业，先受理再据实显示停止结果 |
| 重试 | 保留原失败；按原因新建尝试或只恢复连接；不重复消耗旧授权或伪造用户消息 |
| 归档与恢复 | 归档不删除证据；活动工作先明确处置；归档区能重开/恢复，恢复不自动启动运行 |

失败、受控阻断、等待批准、用户取消、警告、观察降级分别显示。每个恢复动作必须当前可执行；“平台待建设”不能包装成用户点击即可继续的动作。

### 8.1 AI–Human 协作体验验收基准（2026-09-12）

用户明确要求达到 Codex 等主流 Agent 的交互水准。这里对齐的是协作行为，不是配色或布局：人负责目标、关键取舍和授权，Agent 负责推进、解释和维护执行证据。官方协议明确区分开始、运行中补充、按当前回合停止和历史恢复；这给出了可验证的行为参照，不等于本产品已经拥有同等体验。[Codex 回合协议](https://learn.chatgpt.com/docs/app-server#turns)

| 验收 ID | 陌生用户操作 | 必须观察到的产品行为 | 验证方式 |
| --- | --- | --- | --- |
| UX01 委托 | 一句话说目标，不知道模型名或数据格式 | 先理解目标并推进可做的研究；一次只问真正阻塞的问题，不启动固定字段问卷 | 图像、文本、语音三个未预置需求分别走真实多轮对话 |
| UX02 过程可读 | 想知道现在在做什么 | 对应 AI 回合下有动作与必要进展；当前动作、等待条件、下一步清晰；无伪造百分比和装饰专家 | 对照同 task/run/session/turn/call 的后端事件 |
| UX03 随时介入 | 执行中追问、补充或说“先不训练” | 明确补充是否进入当前推理、排队或需要停当前作业；停止控制不排队，目标变更使旧批准失效 | 真实在途输入、旧回合迟到响应、改目标后的审批负例 |
| UX04 就地决策 | 审批前问为什么，拒绝后改方案 | 可解释具体动作、数据范围、资源预算、影响与替代方案；追问不算批准；拒绝不是整个任务失败 | 两轮解释后批准同摘要、修改后拒绝旧摘要、重复点击幂等 |
| UX05 可恢复 | 断网、刷新、关闭再打开、取消后重试 | 回到同任务和同证据；状态不明就核验，不自动重跑；重试保留原尝试且按新计划批准 | 持久化重启/故障注入/精确容器清理证据 |
| UX06 结果可验证 | “给我看看效果，哪里还不行” | 就地打开样本、输出、对照和错例；区分执行成功、质量达标、可发布；技术日志默认折叠 | 真实结果和失败结果各走一次，并核对领域证据 |

PC 的输入焦点、中文输入法、滚动停留、流式布局稳定、键盘操作、长结果阅读和多任务切换属于同一验收，不另做移动版。固定检查 1280×800、1440×900、1920×1080；不得用静态截图代替以上交互验证。

对标记录至少包含任务成功率、有效人工干预次数、重复询问/无效确认次数、停止受理时延、刷新身份/证据保留率与用户能否说清当前状态。相同需求、材料、资源与完成判据下再做对照；未完成真实旅程对照前，不声称“体验已追平”。ONNX 试跑只是 UX04/UX05/UX06 的首个执行消费者，不定义通用能力范围。

## 9. 经验资产不是聊天记忆

一条候选经验至少关联：任务输入输出特征、数据统计与授权范围、来源与环境版本、资源实测、干预差异、验证条件、结果、失败范围和原始证据引用。

入库规则：证据不足的不成为已验证建议；相关不等于因果；有效经验附适用条件与反例；环境/数据变化需重验；允许撤销或降级。默认只在当前任务/工作区复用，跨任务与跨客户共享单独授权，不复制私有样本、权重、凭据或终测内容。

收益证明：完整系统与关闭经验库的同版本比较。经验库在留出任务前冻结，不能把留出结果写入后再重复测量宣称泛化提升。

## 10. 范围、优先级与完成定义

本轮目标版包括：开放任务接入、动态工程执行、可信评测与错例改进、PC 可恢复交互、经授权环境中的可复验交付。

不纳入本轮默认范围：手机端、多租户 SaaS、计费、企业权限全套、无人审批公网部署、云/GPU 自动采购、未经授权的声音克隆、训练任意大型基础模型的保证。生产部署能力另立项，不用 GitHub 发布或 Bundle 下载代替。

优先顺序：通用执行前提与安全资格链 → 可信评测/错例改进闭环 → 预算决策与经验收益 → 跨任务验证和可交付候选版。所有阶段同时保持自然对话、恢复能力与现有训练回归。

完成必须同时具有：

1. **通用性证据**：未预装方案的留出任务，在冻结主干后由 Agent 完成任务工程；不能靠研发临时补场景代码。
2. **领域收益证据**：相同底模与资源条件下，达到已批准的质量/效率/人工介入目标；没有收益就报告未证实。
3. **产品闭环证据**：每条关键 PC 旅程满足真实对象变化、持久化、身份连续、重入恢复、状态约束、失败取消六项。
4. **交付证据**：独立测试、干净环境消费、源码安装、Git/CI/Release 分开核验。任何一项不能用其他项推定。

具体工作包、样例矩阵和退出门见[迭代计划](ITERATION-PLAN.md)。
