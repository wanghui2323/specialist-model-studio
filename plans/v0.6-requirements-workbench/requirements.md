## 2. 本轮要解决的问题

用户不应该进入一个“换了提示词的开发者 Harness”。用户应该进入一个新的模型训练产品：

1. 用一句业务语言创建一个有 `task_id` 的训练任务；
2. 在同一任务里对话、交数据、确认训练合同、批准关键操作；
3. 看见真实工具调用、训练事件、指标、失败样本和制品；
4. 刷新页面后能回到同一任务和同一 Agent 会话；
5. 运行时不可用时明确失败，绝不批量播放预设步骤冒充执行。

这套产品不应该被做成“模型训练表单集合”。前端的长期定位是一套面向普通用户的通用 Agent Workbench：

- 中央工作区承载对话、任务规划、工具调用、等待、批准和恢复；
- 右侧 Context 区根据当前对象展示模型、数据、训练、评测和制品；
- 模型训练能力以领域插件接入同一个 Agent 交互框架；
- 用户不需要理解开发者 Harness 的 Session、Sandbox 或 Workspace 术语。

## 3. 产品对象与所有权

### 主对象：Training Task

`Training Task` 是用户可识别、可恢复、可审计的主对象。它拥有：

- 业务目标与预测目标；
- 数据集版本与体检报告；
- 当前已确认的训练合同；
- 运行血缘、指标、失败样本和制品；
- 一个可恢复的 Agent 会话映射。

### 能力请求与 Recipe 构建请求

每个 Training Task 同时保存机器可读的能力请求：数据模态、训练目标、目标字段/标签、主要指标、资源限制和部署约束。系统先用这些字段匹配 Recipe：

- 已有 Recipe：直接进入数据导入和合同确认；
- 没有 Recipe：持久化 `Recipe Build Request`，由 Code Agent 生成插件、合同测试和验证证据；
- 未经验证的 Recipe 不得执行用户数据或进入“已支持”状态。

因此，“支持任意训练场景”指任意场景都有可继续完成的扩展路径，不是核心代码预装所有模型，也不是把未实现能力伪装成可用。

### DSH 只提供底层组件能力

| 能力 | 所有者 | 用户是否直接看到 DSH 术语 |
|---|---|---|
| 会话与 Agent Loop | DeepSeek Harness | 否 |
| 工具注册与调用 | DeepSeek Harness + Model Harness 插件 | 只看“读取任务、启动训练”等领域动作 |
| 问题与临时审批 | DeepSeek Harness | 只看产品化的问题卡和批准卡 |
| 任务、数据、合同、运行与指标 | Model Harness 后端 | 是，作为唯一事实源 |
| 产品导航、对话、阶段和证据 | Model Harness 前端 | 是 |

## 4. 第一条完整用户旅程

1. 用户输入：“我想训练一个零件颜色分类模型”。
2. 系统创建持久化训练任务并返回稳定 `task_id`。
3. 产品为该任务创建或恢复 DSH 会话，Agent 先读取任务真实状态。
4. Agent 告诉用户缺少数据；用户从产品界面导入 ZIP。
5. 后端真实体检数据，界面和 Agent 都读取同一份报告。
6. 用户检查数据授权、标签含义和验收门槛，冻结训练合同。
7. 用户要求开始训练；Agent 发起关键操作批准。
8. 用户允许一次，后台创建真实 `run_id` 并产生版本化事件。
9. 产品显示真实阶段、指标、失败样本、优化建议和可下载制品。
10. 用户拒绝某个优化策略时，后端不产生新的子运行。

## 5. 前端产品蓝图

### 通用 Agent Workbench

| 区域 | 主要职责 | 模型训练场景中的内容 |
|---|---|---|
| 左侧 Projects / Tasks | 找回项目、任务和最近会话 | 训练任务、状态、最近运行 |
| 中央 Agent Canvas | 对话、计划、工具执行、问题与批准 | 目标澄清、数据请求、训练计划、工具卡、运行过程 |
| 右侧 Context Workspace | 当前对象的结构化、可视化结果 | 模型卡、数据分布、训练曲线、评测矩阵、失败样本、制品 |

中央区需要同时呈现三种状态：

1. **计划状态**：目标、当前步骤、下一步和阻断条件；
2. **执行状态**：工具名称、输入摘要、运行中/成功/失败、真实耗时；
3. **协作状态**：需要用户回答、批准、选择或补充数据的具体问题。

右侧区不是固定仪表盘，而是 Context-sensitive Workspace：

- 选中模型时显示 Hugging Face Model Card、任务类型、License、参数量、文件、依赖和本机兼容性；
- 选中数据时显示版本、授权、标签、样本量、分布、重复、坏样本和预览；
- 训练中显示运行阶段、资源占用、日志、指标曲线和 checkpoint；
- 评测后显示门槛、混淆矩阵、失败样本、候选比较和优化建议；
- 交付时显示模型制品、哈希、推理示例和血缘。

### 2C 视觉与交互原则

- 首屏直接进入可操作的任务，不做营销落地页；
- 信息密度高但不使用开发者控制台式的黑底日志墙；
- 对话是主路径，结构化面板负责理解和决策，不与对话争夺主次；
- 工具调用用领域语言解释“正在做什么、为什么做、产生了什么”；
- 动画只表达状态变化，不用于模拟耗时；
- 桌面端优先三栏，移动端以任务抽屉 + 对话主区 + Context 底部面板重排。

## 6. Hugging Face 连接能力

目标链路是：

`搜索模型 → 阅读 Model Card → 兼容性检查 → 人工批准下载 → 固定 revision → 本地缓存 → 构建训练配置 → 调优 → 评测 → 记录血缘`

必须保留的安全与产品边界：

- gated/private 模型的 Token 只保存在本机凭证层，不写入任务、日志或 Git；
- 下载前展示 License、模型大小、磁盘占用、任务类型与本机资源要求；
- 每次使用都固定 repository + revision/commit hash，避免“同名模型漂移”；
- 下载、构建、训练是不同状态，不得将“模型已选中”展示成“训练可用”；
- 只有与已实现 Recipe 兼容的模型才能进入一键构建，其余模型只允许收藏或生成适配任务；
- Hugging Face Hub 是模型与数据资产源，不替代 Model Harness 的任务、合同、运行与评测事实源。

## 8. 本轮明确不做

- 不声称某个尚未通过 Recipe 验证的 OCR、语音、目标检测或时序场景已经可以训练；这类任务进入 Recipe Build Request，而不是被拒绝或伪装执行；
- 不允许 Agent 在没有兼容性检查与用户批准时自动下载任意 Hugging Face 模型；
- 不做云端多租户、权限体系、生产发布或线上推理服务；
- 不 Fork DeepSeek Harness，也不复制其通用开发者 Web；
- 不做与真实任务证据分离的“教学演示流程”；
- 不以动画、定时器或预置消息模拟训练进度。

## 9. 需要用户确认的 8 个决策

1. **通用前端框架**：先搭建可复用的 Agent Workbench，模型训练作为第一套领域 Context，而不是写死一个训练页面。
2. **三栏交互**：左侧任务、中间计划/对话/工具、右侧 Context 可视化作为桌面端主结构。
3. **最低验收场景**：v0.6 至少跑通图片多分类与表格回归；它们只验证通用内核，不限定后续训练场景。
4. **建任务方式**：用户第一次发送消息时，产品先创建 Training Task，再把同一目标交给 Agent。
5. **DSH 可见度**：`3080` 只保留内部调试入口，不出现在正常用户导航里。
6. **人工门禁**：数据授权、标签检查、验收门槛、模型下载、启动训练和执行优化都需要可追溯的人类决定。
7. **Hugging Face 首轮深度**：建议首轮完成搜索、模型卡、兼容性检查和批准下载；实际构建与调优只对已实现 Recipe 开放。
8. **发布门槛**：只有真实对话、拒绝不变更、刷新恢复、桌面/移动端验证全部通过，才提交并推送 GitHub。

## 11. 迭代 Loop

每一轮都按同一闭环推进：

`需求合同 → 最小实现 → 真实运行 → 证据审查 → 用户确认 → 合并或回退`

硬规则：

- 一轮只解决一个可验证的用户结果；
- 开发状态和验证状态分开记录；
- 没有证据的任务不能标记完成；
- 用户未确认前，任务保持 `planned`，不进入 `in_progress`；
- 如果新信息改变产品边界，先更新本需求合同，再继续编码。
