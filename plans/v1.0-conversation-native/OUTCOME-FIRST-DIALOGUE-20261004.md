# 通用对话引导修复 · 2026-10-04

## 问题与规则

原对话把准备建议做成了材料盘点问卷：目标和路线已经明确，仍然追问是否有材料、是否从零收集、是否改选路线。三层提示词的重复规则以及任务工具的“待确认”状态，又使咨询被误当成执行审批。

用户要求通用修复，因此不再保留语音等场景的专门话术。共享策略位于 `integrations/deepseek-harness/consultation-policy.js`，在领域执行契约后挂载一次；persona 与每轮 host 指令只补充角色、任务身份和授权约束。

- 目标、输出和路线明确后，直接给数据规格、准备步骤、带假设的资源参考、最小实验及验收方法。
- 现有材料按相同规格检查；尚无材料则按规格准备，不先做“有没有材料”的问卷。
- 只有用户独有、尚未知、会改变紧接着行动且不能通过工具、合理假设或条件分支解决的问题，才值得追问。
- 已选路线不反复确认；从头/从零训练按随机初始化理解，可以先做小架构验证，不偷换成微调，也不一律等同于大型通用预训练。
- 原任务状态、合同、模型绑定、资源适配和运行授权门禁保持。执行前置条件不限制准备建议，状态文案明确区分两者。
- 当前接入缺口说明具体待办，不据此断言业务目标不可行；模型输出仍需真实行为复验，提示词断言不能保证所有回复。

## 实现

增加无任务、无计划、无需审批的 `GET /resources/local` 和 `model_harness_get_local_resources` 只读工具。返回 CPU、内存、磁盘、加速器检测及运行环境，不返回主机路径、凭据或原始诊断信息。`observation_only=true`，不代表模型适配或执行授权。硬件检测和当前 CPU-only 执行策略分开。

后端保留原始 bytes 并计算 GiB 字段，避免模型自行换算容量；例如 `19327352832 bytes = 18 GiB`。未知容量保持 `null`。

普通消息和新对话成功不再显示“消息已发给 AI”或额外成功横幅。排队、检查点讨论、错误与重试反馈保留。页面资源版本为 `2.4.21-pc-rc`。

## 验证与范围

全量 Python 运行了 687 项，初次有 2 项旧提示词字面断言失败，其余通过；对应断言按新共享策略和只读例外修正后单独复验。新增 GiB 转换另有参数化测试。Node 全量及真实工具调用、策略实际打包、消息发送状态矩阵单独复验；Node 最终 244/244；两项失败过的 runtime 方法与 host 共 4/4；GiB 测试 4/4。

真实 DeepSeek 验证覆盖本机配置、从零语音、从零图片分类与文本微调。前两轮仍出现重选路线、过强数据规模断言或容量误报，原始响应完整保留；这些失败不能被当成通过证据。最后一轮结果在 `runs/acceptance/20261004-generic-consultation-ready/`，前两轮在同级 `20261004-generic-consultation/` 与 `20261004-generic-consultation-final/`。

最后一轮语音与图片均先给准备方案、保留从零路线、没有创建结构化问卷，内存值正确为 18 GiB。但语音尾部仍追加可省的问题，部分数值要求过强，文本准备出现过度来源检索和失败动作。因此对话质量只记为有改善，尚未全量验收通过。详见 `20261004-generic-consultation-ready/review.json`。

此前表格回归、数值标签分类和图片分类的真实导入、合同、训练、评估、独立新样本、打包、下载和重启验证仍保留在 `20261004-release-repair/`、`20261004-product-visual/`。本轮不把语音训练、GPU 调度或任意仓库执行声明为已接通。
