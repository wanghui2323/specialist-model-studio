# Specialist Model Studio：AI-Human 训练交互方案

> 状态：已由产品负责人确认，2026-08-26；进入三轮实现与验收
> 参考：WorkBuddy 真实模型训练过程、现有 Figma 状态稿、Specialist Model Studio 的训练对象与证据合同
> 原则：借鉴 WorkBuddy 的对话与产物协作方式，不复制其界面，也不继承其状态冲突

## 1. 方案结论

产品不再以“固定训练步骤面板”为主，而采用一个 **对话主导、任务持续运行、产物按需展开**
的 AI-Human 工作台。

- 对话是唯一主入口：用于澄清目标、解释计划、请求确认、报告变化和接受干预。
- 后台 Run 拥有独立生命周期：对话回复结束不代表训练结束。
- 右侧 workspace 默认关闭：只有查看计划、模型比较、数据检查、训练曲线、评测报告或
  artifact 时才展开。
- 多智能体是真实编排能力，不是常驻的角色橱窗：协调器统一对用户说话，专家在真实委派
  发生时以执行组形式出现。
- 任何“完成、成功、可发布”都由 task-owned 对象和证据决定，不能由聊天文案或动画决定。

## 2. 页面结构

### 2.1 桌面端

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 任务标题  ·  当前真实状态                         证据  ···                │
├──────────────┬──────────────────────────────┬──────────────────────────────┤
│ 训练任务      │                              │ 按需 workspace               │
│              │        对话主线               │                              │
│ 最近任务      │  用户目标                    │ Plan / Model Compare         │
│ 状态与时间    │  AI 澄清 / 执行摘要          │ Data Inspector               │
│              │  决策卡 / Action 组           │ Live Run / Evaluation        │
│              │  结果卡                       │ Artifact / Release           │
│              │                              │                              │
│              │  ┌────────────────────────┐  │                              │
│              │  │ 可持续干预的 composer  │  │                              │
│              │  └────────────────────────┘  │                              │
└──────────────┴──────────────────────────────┴──────────────────────────────┘
```

- 左栏：约 248px，只保留任务切换、真实状态和更新时间，不承载训练配置。
- 中栏：默认 720–840px 的阅读宽度，是产品的主要操作面。
- 右栏：480–600px，默认不占位；展开后压缩中栏但不遮挡当前 HumanCheckpoint。
- 顶栏：只保留任务名、一个权威状态和“任务证据”，删除重复阶段、连接状态和说明文字。

### 2.2 窄屏与移动端

- 900–1279px：任务栏折叠；workspace 作为右侧覆盖层。
- 小于 900px：对话单列；任务列表和 workspace 都进入全屏 sheet。
- HumanCheckpoint、停止动作和发送按钮始终可触达，不把桌面三栏直接压缩到移动端。

## 3. 一条完整的 AI-Human 主流程

### 阶段 A：目标形成

用户可以只说“帮我训练一个时序模型”。协调器先用自然语言复述当前理解，再只询问会改变
技术路线的最少问题，例如：

> 你是想预测未来数值、识别异常，还是给一段时序分类？这会决定数据格式和评测方式。

以 2–4 个快捷选项配合自由输入。此时不展示 Recipe、Adapter、schema 或能力探测日志。

### 阶段 B：方案形成与确认

目标足够明确后，协调器可以委派模型研究、数据和资源专家，并把结果压缩成一张方案卡：

- 我理解的目标与验收指标；
- 数据还缺什么；
- 推荐模型及备选模型；
- 本机是否能运行；
- 将执行哪些动作、需要哪些权限、何时暂停。

用户可以“按推荐方案继续”“修改方案”或“先只准备数据”。确认绑定精确 plan revision，
不能以一段长聊天文本代替授权对象。

### 阶段 C：真实执行

对话只持续回答四件事：刚完成什么、现在做什么、遇到什么、是否需要用户。

真实 Action 以紧凑执行组呈现：

- 默认只显示动作名、负责专家、状态、耗时和最后心跳；
- 展开后显示脱敏命令、输入输出 ObjectRef、退出码和日志；
- 并行动作显示真实依赖关系，不使用前端定时器模拟轮次；
- 对话回合结束后，只要后台 Run 仍运行，顶部继续显示“后台训练中”。

### 阶段 D：需要用户时

只有会改变目标、成本、权限、数据解释或发布结果的问题才暂停。问题以 HumanCheckpoint 卡
呈现，必须同时包含：

- 为什么现在需要决定；
- 推荐选项；
- 每个选项的影响；
- 不回答时的安全默认动作。

输入框仍保留自由输入，但当前唯一待办视觉上高于执行证据。

### 阶段 E：结果与下一轮

训练和评测完成后，对话只给一句结论、核心指标、质量门判断和建议动作；完整内容在右侧
EvaluationReport 中查看。

如果候选比基线差，正确终态是：

> 实验已经完成，但候选模型比基线退化 0.33 个百分点。本次不发布，建议保留基线并调整
> 数据或训练策略。

“继续优化”“导出候选”“结束实验”是当前动作；“发布”必须保持禁用。

## 4. 七类核心交互形态

| 形态 | 用户看到什么 | 何时出现 | 不应该出现什么 |
| --- | --- | --- | --- |
| 自然对话消息 | 理解、结论、下一步 | 澄清、阶段转场、结果 | 后端 schema、整段日志、机械状态播报 |
| 轻量思考/计划状态 | “正在核对数据格式”等一句可撤销状态 | 模型组织下一步时 | 原始思维链、“深度思考”营销标签 |
| Action 执行组 | 动作、专家、状态、耗时、心跳 | 真实工具或后台任务存在时 | 前端虚构步骤、无 ID 的成功动画 |
| HumanCheckpoint | 一个问题、推荐项、影响、确认动作 | 必须人工决定时 | 独立表单与聊天重复问同一问题 |
| Artifact/中间结果 | 模型比较、数据检查、资源报告的入口 | 产生 task-owned ObjectRef 后 | 无来源的静态卡片、自动拼接假指标 |
| Evaluation/Verdict | 基线、候选、差值、质量门、下一动作 | 真实评测完成后 | “训练完成”直接等同“优化成功” |
| 风险/恢复卡 | 真实原因、影响、推荐安全动作、恢复入口 | blocker、失败、取消或资源超限时 | 泛化的“等待确认”、把安全停止写成“用户取消” |

错误和取消不另建一套页面，而是上述 Action 或 Run 的真实状态：`failed_recoverable`、
`blocked`、`cancelling`、`cancelled`、`stopped_with_checkpoint`。

## 5. 多智能体应该如何被用户感知

### 默认层

用户只与“训练协调器”对话。协调器可以说：

> 我正在让模型研究、数据和资源三位专家并行核对，数据格式确认后我会给你一个可执行方案。

下方显示一个可展开的“专家协作”执行组，而不是四个 Agent 各自发送长消息。

### 展开层

只有真实 child session / delegation 存在时才展示：

- 专家名称与本轮职责；
- 正在执行的 Action；
- 当前状态和最后心跳；
- 产出的 ObjectRef；
- 返回协调器的结论。

推荐的动态角色池包括：需求与任务专家、模型研究专家、数据专家、训练执行专家、评测与
发布专家。并非每个任务都要启动全部角色，也不允许前端预先画出“多智能体正在协作”。

## 6. 右侧 workspace 的开启规则

workspace 不是固定仪表盘，也不是第二条工作流。

| 触发 | 默认打开内容 | 自动打开 |
| --- | --- | --- |
| 用户点击模型推荐 | Model Compare | 是 |
| 用户需要确认训练计划 | Plan Revision | 是 |
| 数据检查产生异常 | Data Inspector | 是 |
| 普通工具调用或下载 | 不打开，仅保留 Action 组 | 否 |
| 训练运行中 | 用户点击后打开 Live Run | 否 |
| 评测完成 | EvaluationReport | 首次生成时自动打开；用户主动关闭后不反复打开 |
| 产生可交付 artifact | Artifact Detail | 用户点击后 |

关闭 workspace 不改变任务状态；刷新和从任务列表重入时，应恢复同一个 task-owned
ObjectRef，而不是恢复一个前端 tab 名称。

## 7. 视觉与品牌方向

定位是“面向个人开发者和 AI 产品经理的专业模型智能工作台”，因此采用 **轻量消费级外观 +
专业执行密度**，避免传统 MLOps 控制台或 AI Coding 模板感。

- 基底：暖灰白和中性灰；品牌紫只用于主动作、焦点和协调器身份。
- 语义色：运行蓝、等待琥珀、成功绿、阻断红、取消灰，不能所有状态都用紫色 pill。
- 字号：正文 15–16px，辅助 13px，任务标题 20–22px；不使用大面积粗体。
- 圆角：输入框和重要结果 14–16px，普通执行行 8–10px；减少卡片套卡片。
- 阴影：只用于浮层和 workspace，内容分组主要依靠留白、分隔线与字号层级。
- 动效：只表达真实状态变化；运行中采用低频脉冲/进度，不循环播放“完成过程”。
- 图标：统一线性图标；Agent 头像体现职责但不使用彩色卡通角色。
- 品牌：保留 Specialist Model Studio 名称与 `H` 形核心标识，强化“训练任务、证据、结果”
  三个产品语义，不把 DeepSeek Harness 暴露为主品牌。

## 8. 从 WorkBuddy 保留、改造和拒绝的部分

### 保留

- 对话主线；
- 长任务的真实进度列表；
- 执行过程中允许用户继续输入；
- 对话结论与右侧文档/报告协同；
- 阶段结果自然驱动下一阶段。

### 改造

- 把任务列表改为真实 work item / ActionEvidence 投影；
- 把“回复完成”与“后台 Run 完成”拆开；
- 把长授权文本改为可审计的批准卡；
- 把技术说明压缩为人能理解的摘要，证据按需展开；
- 把结果报告变成 task-owned 对象，而不是旁路 Markdown。

### 不照搬

- 计划文档和实时状态互相冲突；
- composer 残留已提交授权或出现语义不明的第二条草稿；
- “用户已取消”覆盖安全停止、系统停止和真正用户取消；
- “深度思考”“生成回复中”冒充训练进度；
- 对话结束后遗留后台进程；
- 用“训练完成”表达“模型优化成功”。

## 9. 确认后的实现范围

### 第一轮：结构和状态

- 收敛为任务栏 + 对话 + 自适应 workspace；
- 实现七类交互组件和顶部单一状态；
- 对话回复、后台 Action、TrainingRun 与 HumanCheckpoint 分层展示；
- 时序模糊需求必须先进入真实澄清卡。

### 第二轮：训练过程

- 接入真实专家委派和 Action 执行组；
- 接入干预、排队、停止并替换三种 composer 语义；
- 接入资源预检、训练心跳、取消级联和 checkpoint 状态。

### 第三轮：结果和验收

- 接入 EvaluationReport、基线/候选差值和质量门；
- 接入右侧报告、artifact、发布/回滚决策；
- 用时序任务和 ASR/图像任务各完成一条桌面与移动端真实浏览器闭环。

## 10. 本轮需要确认的五个判断

1. 主界面采用“任务栏 + 对话主线 + 按需 workspace”，不再保留固定右侧五标签仪表盘。
2. 协调器作为唯一对话人格，专家只在真实委派发生时以执行组展开。
3. 模型比较、计划确认、数据异常和最终评测可自动打开 workspace；普通工具执行不自动打开。
4. 视觉采用暖中性色 + 克制品牌紫，专业但不做传统 MLOps 控制台。
5. 下一轮先完成结构与七种真实交互形态，再做训练图表、artifact 和发布细节。
